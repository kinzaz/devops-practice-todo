## 1. Назначение документа

Это самостоятельный документ для передачи контекста другой модели. Он описывает учебный проект, инфраструктуру, процедуры выпуска, пройденные упражнения и ограничения. Читать его перед предложением следующих шагов.

Источники достоверности:

- Исходники, тесты и workflow сверены с локальными файлами при подготовке документа.
- Изменения на Ubuntu и результаты запусков GitHub Actions подтверждены пользователем в ходе обучения. При подготовке документа повторное подключение к серверу не выполнялось.

## 2. Пользователь, цель и формат обучения

Пользователь — **fullstack-разработчик**, изучает DevOps с нуля на собственном приложении. Базовое устройство React, API и HTTP ему знакомо. При этом нужны объяснения Linux, SSH, прав, systemd, Nginx, DNS, TLS, CI/CD и эксплуатации.

Предпочтительный формат:

1. Объяснить задачу, принцип работы и причину выбранного решения.
2. Дать небольшое практическое упражнение с ожидаемым результатом.
3. Явно указывать, где выполнять команды: **Mac**, **Ubuntu под devops** или **GitHub UI**.
4. Пользователь выполняет действия самостоятельно и сообщает результат. Не заменять обучение незапрошенными автоматическими изменениями сервера.
5. Разбирать ошибки и альтернативы. Не переходить сразу к большому набору инструментов.

**Docker сознательно отложен пользователем.** Прежде чем продолжать контейнеризацию, обсудить с ним следующий этап. Docker, Compose, Kubernetes и Prometheus в текущую рабочую архитектуру не входят.

Первоначальный усложнённый проект заметок с Docker/PostgreSQL/метриками был заменён простым todo. Не считать первоначальную реализацию актуальной.

## 3. Краткое состояние на момент передачи

- Приложение работает на удалённой Ubuntu, доступно по HTTPS.
- UI: React + Vite. Backend: FastAPI + Uvicorn. База: SQLite.
- Nginx отдаёт UI и проксирует `/api/` в Uvicorn.
- API выполняется как служба systemd под отдельным пользователем `todo`.
- Код выпускается в отдельные каталоги, выбранный релиз задаётся ссылкой `current`.
- UI и backend выпускаются раздельно через ручной запуск GitHub Actions.
- CI автоматически запускает тесты API и собирает UI; настроена обязательная проверка для слияния в `master`.
- Проверены ручные и автоматические откаты UI и backend, включая учебный провал проверки после выпуска.
- Данные вынесены из каталогов релизов. Сделаны и проверены ручные резервные копии и восстановление.
- Следующий этап обучения не выбран: пользователь попросил сначала систематизировать сделанное и изучить альтернативы.

## 5. Приложение и исходники

```text

  test_api.py

```

Todo позволяет создать задачу, получить список, отметить выполнение и удалить задачу. Данные хранятся на сервере, не в localStorage. Авторизации и отдельных пользовательских аккаунтов приложения нет.

API:

| Метод | Путь | Результат |
|---|---|---|
| GET | `/api/todos` | Задачи, новые первыми |
| POST | `/api/todos` | Создание, статус 201 |
| PATCH | `/api/todos/{id}` | Изменение `done` |
| DELETE | `/api/todos/{id}` | Удаление, статус 204 |
| GET | `/api/version` | `{"version": "<SHA>"}` в автоматическом релизе |

Название задачи: после удаления пробелов по краям от 1 до 200 символов. Пустое название отклоняется. Несуществующая задача при изменении/удалении даёт 404.

SQLite-таблица: `todos(id INTEGER PRIMARY KEY, title TEXT NOT NULL, done INTEGER NOT NULL DEFAULT 0)`. Таблица создаётся через `CREATE TABLE IF NOT EXISTS` при старте. Системы миграций пока нет.

Backend выбирает базу через `TODO_DATABASE`. Без этой переменной используется `todo.db` рядом с `app/main.py`; это поведение для локального запуска. На сервере переменная обязательно указывает на постоянный каталог данных.

Версия считывается при импорте модуля из `revision.txt` в корне конкретного релиза. Если файла нет, значение — `development`. Значение хранится в `APP_VERSION`: смена ссылки на диске не должна заставлять старый процесс сообщать SHA ещё не загруженного кода.

Текущие runtime-зависимости:

```text
fastapi>=0.115,<1
uvicorn>=0.34,<1
```

Для разработки дополнительно используются pytest и httpx. `pyproject.toml` существует, но зависимости реально устанавливаются из `requirements*.txt`; полноценный packaging через pyproject не настроен.

Frontend использует React 19 и Vite 6 по диапазонам в package.json. В UI осталась учебная подпись `v0.2.0`: она **не является достоверным номером текущего деплоя**. Для него используется `release.txt`.

## 6. Локальная разработка и прокси Vite

На Mac API запускается из корня проекта:

```sh
source .venv/bin/activate
python -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

Во втором терминале:

```sh
cd /Users/kinzaz/Documents/devOps/frontend
npm run dev
```

Vite слушает `127.0.0.1:5173`, `strictPort: true`. Его `server.proxy` передаёт `/api` на `http://127.0.0.1:8000`.

React использует относительный адрес `fetch('/api/todos...')`. Поэтому браузер отправляет запрос на origin открытой страницы:

- локально запрос принимает Vite и проксирует в локальный API;
- на сайте запрос принимает Nginx и проксирует в API на Ubuntu.

`vite.config.js` не выполняется в браузере. Настройка dev-прокси не встраивается в production-сборку. Команда `npm run build` создаёт `frontend/dist`; для её отдачи Node.js на сервере не требуется.

| Пользователь Ubuntu | Назначение |

На Mac использовались:

- соответствующие файлы `.pub` — публичные части.

Ключ автоматизации создан без passphrase, чтобы работать без интерактивного ввода. Его закрытая часть хранится в GitHub Actions Secret, а не в репозитории.

Подтверждённый через консоль провайдера отпечаток ED25519-ключа сервера:

```text
SHA256:RWOJSRaYG+Ekwdr5lLxfG9poSTu4kGWTfPQ0cNf161k
```

Это публичный отпечаток сервера, не личный ключ пользователя. При первоначальном подключении была обнаружена смена ключа для IP; сначала сверили новый отпечаток через консоль провайдера, затем продолжили. Не обходить последующие несовпадения без новой проверки.

Права:

- Родительские каталоги `/var/www/todo-releases` и `/opt/todo/releases` переданы `deploy`; он создаёт релизы и переключает ссылки внутри них.
- Старые ручные релизы могут принадлежать `devops`; смена владельца родительского каталога не была рекурсивной.
- Новые backend-релизы создаются с `umask 022`, чтобы `todo` мог читать код и выполнять Python.
- `/var/lib/todo`: владелец `todo:todo`, права 750.
- `/var/lib/todo/todo.db`: владелец `todo:todo`, права 600.

В `/etc/sudoers.d/todo-deploy` через visudo добавлено:

```sudoers

```

Разрешена точная команда перезапуска конкретной службы, не произвольный sudo. В workflow используется `sudo -n`, чтобы при недостатке прав завершаться ошибкой вместо запроса пароля.

В переписке ранее раскрывались пароль первоначального root-доступа и секрет в Git remote. **Не переносить их в документы или команды.** Пользователь подтвердил отзыв GitHub-токена и очистку URL remote. Смена первоначального root-пароля отдельно не подтверждена. Для продолжения использовать настроенный SSH-доступ, не искать секреты в старой переписке.

## 9. Nginx, DNS и HTTPS

DNS-запись A для `test-stand.fun` указывает на `201.34.142.215`. При покупке наблюдалась задержка: публичный DNS сначала отвечал NXDOMAIN, затем домен заработал.

В панели также были TXT/SPF и MX-записи Timeweb. Они относятся к почте и не используются todo.

Конфигурация сайта: `/etc/nginx/sites-available/default`, включена через стандартный механизм `sites-enabled`.

Смысл актуальных настроек:

```nginx
server_name test-stand.fun;
root /var/www/todo-releases/current;
index index.html;

location /api/ {
    proxy_pass http://127.0.0.1:8000;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}

location / {
    try_files $uri $uri/ /index.html;
}
```

Это **выдержка**, не полный файл для замены: Certbot добавил отдельные настройки TLS и перенаправления.

Изучено экспериментально:

- `server_name` участвует в выборе блока server по имени запроса, но не является запретом остальных имён.
- При отсутствии совпадения используется `default_server` для адреса/порта; если он не задан явно, роль получает первый подходящий server.
- В `proxy_pass http://127.0.0.1:8000;` нет завершающего `/`: в данной конфигурации сохраняется путь `/api/...`.
- `try_files` с fallback на `index.html` позволяет обслуживать клиентские маршруты SPA.

HTTPS настроен бесплатным Let’s Encrypt через Certbot, установленный Snap. Платный Timeweb Pro SSL не покупали.

Основные пути:

```text
/etc/letsencrypt/live/test-stand.fun/fullchain.pem
/etc/letsencrypt/live/test-stand.fun/privkey.pem
/etc/letsencrypt/options-ssl-nginx.conf
/etc/letsencrypt/ssl-dhparams.pem
```

Сертификат/цепочка и публичный ключ доступны клиентам; закрытый TLS-ключ остаётся на сервере. Эти ключи не связаны с SSH-ключами.

Certbot настроил HTTPS на 443 и перенаправление с HTTP. Пользователь подтвердил выполнение этапа с `certbot renew --dry-run`. Текущее расписание и срок сертификата при фиксации документа заново не проверялись.

## 10. Systemd и постоянные данные

Путь службы: `/etc/systemd/system/todo.service`. Её существенная конфигурация после выполненных упражнений:

```ini
[Unit]
Description=Todo API
After=network.target

[Service]
User=todo
Group=todo
WorkingDirectory=/opt/todo/releases/current
ExecStart=/opt/todo/releases/current/.venv/bin/python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
Restart=on-failure
RestartSec=3
Environment=PYTHONUNBUFFERED=1
Environment=TODO_DATABASE=/var/lib/todo/todo.db

[Install]
WantedBy=multi-user.target
```

Это восстановленная по выполненным шагам конфигурация; перед редактированием читать фактический unit через `systemctl cat todo`.

Служба включена через `systemctl enable --now todo`.

Изучено:

- Служба `todo` — имя управляемого systemd процесса; запускает Uvicorn, который загружает FastAPI.
- `source .venv/bin/activate` не нужен для systemd: используется абсолютный путь к Python.
- `daemon-reload` требуется после изменения unit, но не после обычного переключения релиза.
- Переключение ссылки не заменяет уже загруженный Python-код: backend требует restart.
- `Restart=on-failure` не отменяет намеренный `systemctl stop`.

Старые пути `/opt/todo/current`, `/var/www/todo-current`, `/opt/todo/app` и исходная база могли сохраниться после упражнений. Они **не являются актуальными точками запуска**. Не удалять их вслепую; сначала проверить использование.

## 12. CI/CD: актуальная реализация

Источник истины: `.github/workflows/ci.yml` в проекте. Workflow называется **Todo CI**.

События:

- `push`;
- `pull_request`;
- `workflow_dispatch` — ручной запуск.

Параметры ручного запуска:

| Input | Значения | Назначение |
|---|---|---|
| `component` | `ui`, `backend`; по умолчанию ui | Какой компонент выпускать |
| `simulate_failure` | boolean, по умолчанию false | Намеренно провалить проверку после активации |

`permissions: contents: read`. Личный GitHub PAT для workflow не используется.

### CI: test-and-build

GitHub-hosted runner `ubuntu-latest`, Python **3.13**, Node.js **22**. Точная версия Python на production Ubuntu отдельно не зафиксирована; не считать её совпадающей с CI.

Последовательность:

1. Checkout исходников; `persist-credentials: false`.
2. `pip install -r requirements-dev.txt`.
3. `python -m pytest -q`.
4. В `frontend`: `npm ci`, затем `npm run build`.
5. Сохранение UI-артефакта `todo-ui-${github.sha}` из `frontend/dist/`.
6. `git archive` коммита HEAD, только `app` и `requirements.txt`, в `backend.tar.gz`.
7. Сохранение артефакта `todo-backend-${github.sha}`.

Срок хранения обоих артефактов — 7 дней. Текущие Actions в файле: checkout/setup-python/setup-node/upload-artifact v7, download-artifact v8. Перед будущим обновлением сверять их документацию.

### Общие настройки деплоя

- Jobs: `deploy-ui` и `deploy-backend`, каждый зависит от успешного `test-and-build`.
- Деплой разрешён только при `workflow_dispatch` из `refs/heads/master` и выборе соответствующего компонента.
- Это **continuous delivery с ручным решением о выпуске**, не автоматический выпуск каждого push.
- Каждый deploy-job скачивает артефакт **из того же запуска workflow**. Результат не пересобирается на Mac.
- Имя релиза: `${github.sha}-${github.run_id}-${github.run_attempt}`. Повторные запуски одного коммита имеют разные каталоги.
- SSH выполняется как `deploy` на IP, с `StrictHostKeyChecking yes`, `IdentitiesOnly yes`, `BatchMode yes`.
- GitHub repository secrets: **TODO_SSH_KEY** и **TODO_KNOWN_HOSTS**. Вторая величина — содержимое проверенного known_hosts, не строка SHA256-отпечатка.
- SSH-конфигурация создаётся на runner; alias `todo-server` существует только в этом контексте, не считать его настроенным на Mac.
- Concurrency groups: `todo-production-ui` и `todo-production-backend`; `cancel-in-progress: false`.

### Выпуск UI

1. Скачать артефакт в `ui/`.
2. Проверить `index.html`, добавить `release.txt` с SHA коммита, установить читаемые права файлов.
3. Создать `/var/www/todo-releases/<release>` и загрузить содержимое.
4. Запомнить предыдущий путь `current` через step output.
5. Создать временную ссылку и заменить `current` через `mv -Tf`.
6. Проверить публичный `release.txt`: содержимое должно совпасть с SHA workflow.
7. Проверить доступность `/api/todos`.
8. При `simulate_failure=true` намеренно завершить проверку с кодом 1.

Откат UI выполняется, если активация завершилась успешно, а последующая проверка упала. Перед возвратом проверяется, что current всё ещё указывает на релиз этого запуска. После переключения проверяется главная страница.

Nginx не перезапускается: его конфигурация не меняется при выпуске UI.

### Выпуск backend

1. Скачать `backend.tar.gz` из backend-артефакта.
2. Создать `/opt/todo/releases/<release>` и загрузить архив.
3. Распаковать исходники, создать `.venv` системным `python3` Ubuntu и установить runtime-зависимости.
4. Проверить импорт FastAPI-приложения. Эта проверка не запускает lifespan и не проверяет production-базу.
5. Записать SHA в `revision.txt`.
6. Запомнить предыдущий путь `current`.
7. Проверить наличие кода и Python, переключить ссылку через временную ссылку и `mv -Tf`.
8. Выполнить разрешённую команду `sudo -n /usr/bin/systemctl restart todo.service`.
9. С повторами запросить публичный `/api/version`, разобрать JSON и сравнить version с SHA workflow.
10. Проверить `/api/todos`; при выбранном учебном сбое завершиться с кодом 1.

Откат backend запускается при ошибке активации **или** последующей проверки, если предыдущий путь успешно сохранён. Проверяется, что ссылка указывает либо на неудачный релиз, либо уже на предыдущий; неожиданное внешнее переключение не перезаписывается. Возвращается прежний код и его `.venv`, перезапускается служба, проверяется `/api/todos`.

### Что означает результат отката

Пользователь подтвердил успешные выпуски и учебные автоматические откаты обоих компонентов. После успешного отката весь workflow остаётся **красным**, поскольку выпуск не прошёл проверку. Успех восстановления не превращает неудачный выпуск в успешный.

При повторном выпуске того же SHA версия API может не измениться после отката. Проверять также полный путь current: номера run/attempt различаются.

Это не гарантия восстановления при отмене workflow, потере SSH, отказе VM или недоступности БД. Откат кода не восстанавливает данные.

## 13. Резервное копирование и восстановление

До переноса данных в `/var/lib/todo` выполнено упражнение:

1. Создана задача «Проверка резервной копии».
2. Через SQLite `.backup` создан `/home/devops/backups/todo-first.db` из тогдашней `/opt/todo/app/todo.db`.
3. Проверены SELECT и `PRAGMA integrity_check` → `ok`.
4. Копия скачана на Mac в `~/todo-backups/`.
5. После бэкапа добавлена другая задача.
6. Копия восстановлена через `.restore` в `/opt/todo/restore-check/todo.db`.
7. Отдельный API запущен на 8001 с TODO_DATABASE, указывающим на восстановленный файл.
8. Подтверждено: старая задача есть, более поздней нет. Проверочный процесс остановлен.

После этого production-база перенесена в `/var/lib/todo/todo.db`. **Исторические команды с `/opt/todo/app/todo.db` больше не являются процедурой резервирования актуальных данных.**

Теперь файл принадлежит `todo` с правами 600; обычный devops/deploy не должен читать его без соответствующих полномочий. При следующем упражнении бэкапа нужно использовать актуальный путь и продумать владельца копии.

Расписание бэкапов, ротация, контроль успешности, автоматическое внешнее хранение и регулярные restore-drills пока не настроены. Не считать учебную первую копию свежим backup production.

## 15. Ограничения текущей системы

- Одна VM, один процесс API, локальная SQLite: нет отказоустойчивости при потере сервера.
- Перезапуск backend может давать короткую недоступность; blue-green/rolling update не настроены.
- Runtime-зависимости Python заданы диапазонами, нет lock-файла и фиксации системного окружения. Проверка в CI и установка на production могут использовать разные версии Python/библиотек.
- UI и backend имеют независимые concurrency groups; глобальной сериализации обоих компонентов нет. Если выпуски пересекутся, UI-проверка API может попасть на перезапуск backend.
- Проверки выпуска — smoke checks, а не полный E2E-тест. Успешный GET не доказывает корректность всех операций.
- Нет миграций БД. Возврат Python-кода не отменяет изменение схемы или пользовательских данных.
- Бэкапы пока ручные; нет проверенного автоматического плана аварийного восстановления всей VM.
- Нет настроенных пользователем постоянного мониторинга и оповещений. Первоначально на VM был агент Zabbix провайдера; это не наша настроенная система мониторинга.
- Начальная проверка показывала UFW inactive; актуальные firewall/SSH-hardening настройки не проверялись. Не предполагать ни их наличие, ни отсутствие без проверки.
- Нет аутентификации в todo. Сайт является публичным учебным стендом.
- Настройка VM не описана в Ansible/Terraform. Значительная часть логики релизов находится прямо в YAML, SSH-настройка дублируется между jobs.
- Нет очистки старых релизов, контроля заполнения диска и автоматической ротации резервных копий.

## 16. Карта альтернатив, уже обсуждённых с пользователем

Не смешивать разные уровни решений:

| Вопрос | Наш выбор | Обсуждённые альтернативы |
|---|---|---|
| Где выполняется pipeline | GitHub Actions | GitLab CI/CD, Jenkins, локальный скрипт |
| Как описать подготовку и доставку | Shell в YAML | Ansible, специализированные инструменты вроде Capistrano |
| Что доставлять | Статика и архив Python-кода | Пакет приложения, VM image, контейнерный image |
| Где запускать | Процесс на Linux VM | Контейнер, управляемая платформа |
| Как обновлять | Симлинк и restart | Blue-green, rolling update, замена VM |
| Как воспроизвести сервер | Ручные команды | Ansible; отдельно IaC для создания инфраструктуры |

Наш подход похож на классический release-based deployment с `releases/current`, существовавший до распространения контейнеров и применимый сейчас. Docker не заменяет автоматически GitHub Actions, Nginx, DNS, TLS или необходимость backup.

Ansible может выполняться внутри GitHub Actions; эти инструменты решают разные задачи. GitLab/Jenkins могут выполнять те же pytest/npm/ssh-команды с другой конфигурацией pipeline.

## 17. Короткий runbook для проверки состояния

На Mac:

```sh
ssh -i ~/.ssh/devops_learning devops@201.34.142.215
```

На Ubuntu, чтение состояния:

```sh
systemctl status todo --no-pager
systemctl status nginx --no-pager
systemctl cat todo
readlink -f /opt/todo/releases/current
readlink -f /var/www/todo-releases/current
curl -i http://127.0.0.1:8000/api/version
curl -i https://test-stand.fun/api/version
sudo journalctl -u todo -n 50 --no-pager
sudo tail -n 30 /var/log/nginx/error.log
```

Для диагностики не путать прямой запрос на 8000 и запрос через Nginx. JSON `/api/todos` может содержать пользовательские данные: не выводить его без необходимости.

После изменения Nginx: сначала `sudo nginx -t`, затем reload. После изменения unit: daemon-reload и restart. При обычном выпуске backend: переключение current и restart, без daemon-reload.

Ручной запуск выпуска: GitHub → Actions → Todo CI → Run workflow → master → нужный component. По умолчанию `simulate_failure=false`. Случайно не включать учебный сбой для обычного выпуска.
